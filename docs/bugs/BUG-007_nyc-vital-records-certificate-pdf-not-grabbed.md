## Why this one matters

This is the **decisive original record** for the person. It is an **original source with
primary information** — registered four days after the birth — and it **disproves a `Proven` claim in
the tree**: the certificate's birth date is a full year earlier than the date the tree held.

**And we do not hold the file.**

It also matters structurally. **NYC vital records are the single biggest true-source target in the
project.** The follow-ups generated by the ahn-8 Ancestry run point here again and again — NYC birth
certificates, NYC marriage certificates, NY death certificates. Whatever we do about this site, we
will do dozens of times.

## What happened

Capture `20260714-a860historicalvitalrecordsnycgov-0e30ef2c` contains **only**:

```
media/0-record.pdf     provenance = render:page-pdf     553 KB, 3 pages
```

The certificate itself survives inside that render at **screen resolution**:

```
page 1: embedded image 1220 x 656    (12 KB)
page 2: embedded image  977 x 1082   (429 KB)   <- the certificate, as displayed
```

**No certificate file was captured.** We have a picture of a screen showing the record — the exact
failure BUG-001 and REQ-001 exist to prevent: *a render is not the record.*

**The media grabber used to find the blob URL and fetch it. It no longer does.**

## Probable cause

The page now renders the PDF through **Chrome's native PDF plugin** (`<embed>`), not a link or an
image:

- `querySelectorAll('iframe')` → `about:blank`, `null`
- `querySelectorAll('embed')` → **one embed** (the PDF)
- **No `<a href="....pdf">`**, and **no `<img>`** of the certificate
- The plugin's own toolbar — including its Download button — is **not in the accessibility tree**,
  so it cannot be clicked programmatically (I tried; clicking its coordinates fired nothing).

The real file lives on a **SAS-signed Azure blob**:

```
dorisarchive.blob.core.windows.net/reference/REC0051_VitalRecords/Births/Kings/1887/
    B-K-1887-0011687.pdf?se=…&sp=r&sv=…&sr=b&sig=…
```

The signature is **time-limited and per-session**, so the URL **cannot be reconstructed** — it must be
taken from the page while it is live.

## What is needed

**Capture the blob URL the page actually fetches, and fetch it.** The URL *is* observable — the page
requests it. In order of preference:

1. **Observe the network request** — a `webRequest` listener, or
   `performance.getEntriesByType('resource')` — and pull the
   `dorisarchive.blob.core.windows.net/...pdf?...` URL while the SAS token is still valid. This is
   effectively what the 2026-07-09 path achieved.
2. **Read the `<embed>`'s `src`** — it carries the signed URL.
3. **Failing both, fail honestly:** a page whose *only* media is `render:page-pdf`, on a host known to
   serve record images, must be classified **`image: failed`** so the record stays **UNMINED** rather
   than closing on a screen render.

Please also fold these NYC hosts into whatever "an image was expected here" classification exists —
the same principle as REQ-001 R4.1: **the page should tell us whether a record image exists, and if
one does and we did not get it, the record is not mined.**

## The wider lesson (same shape as BUG-006)

A capture that quietly substitutes **a render of the page** for **the record itself** is precisely the
failure this system exists to prevent — and it is **invisible**. The toast said:

```
Captured birth — 6 assertion(s), verify OK, PDF ✓
```

Everything was green. **Only opening the artifact and measuring it revealed that we were holding a
977×1082 screenshot of the most important record on the line.**
